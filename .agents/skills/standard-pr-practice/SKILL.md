# Standard PR Practice

Implement the user's requested change, open its own scoped PR, clear every existing readiness gate on the current remote revision, and leave it open unless a verified repository administrator explicitly asks the agent to merge it. Stay with it through verified PR readiness, an authorized merge, or a specific external or authorization blocker. Do the work in the active task; do not stop at a plan, diagnosis, first push, or PR link.

This incorporates CI repair, review follow-up, and merge-conflict resolution; no separate skills need to be installed or invoked. **`@cubic-dev-ai` is the only review bot for this workflow.** Use exactly `@cubic-dev-ai review this PR` to request review. Address every finding from its verified GitHub account or app, including top-level and advisory reports. Do not invoke or use another bot as a fallback. Report any independently enforced repository gate separately. The canonical skill lives in `.agents/skills/standard-pr-practice`; Claude Code follows the root `CLAUDE.md` link to that same canonical skill. This repo does not register a separate native Claude Code slash command; use the plain-text request `use standard-pr-practice to <requested change>`. Keep one repository source rather than separate global Codex or Claude Code copies.

## Act immediately in Codex and Claude Code

**Models need to just do things.** In both Codex and Claude Code, treat an authorized request as an instruction to execute now. Begin the necessary tool work in the same turn, make routine implementation decisions, and carry the change through publication and follow-up. Do not substitute a plan, extended investigation, repeated reassurance, or an offer to continue for the requested action.

For a narrow fix, the initial path is: read the supplied failure, resolve repository identity and applicable instructions, use an isolated worktree, inspect the implicated source and its direct callers/tests, implement the coherent fix and regression coverage, inspect the scoped diff, commit, push, and open the PR. Start editing once those inputs establish the change. Do not keep researching after the next implementation step is clear.

Keep pre-publication investigation limited to facts that can change the implementation, authorization, or publication destination. Use one targeted memory lookup when required; do not read historical rollouts, inventory unrelated tools or services, explore unrelated repository history, or repeatedly read instructions without a concrete dependency. Consult the relevant official documentation for the specific API behavior being changed; avoid broad documentation searches and speculative failure catalogues. Start CI and request review after opening the PR, then inspect detailed merge requirements. Required safeguards remain required; perform them once rather than using them to justify repeated discovery.

Prefer a complete, reviewable first implementation over optional refinement. If investigation is expanding, identify the exact unanswered question and make the next action resolve it. If the evidence already supports implementation, stop investigating and edit. If a missing fact truly prevents a correct fix, report that specific blocker promptly while completing independent authorized work. Never fill missing evidence with an invented cause or publish a knowingly incomplete change as a completed fix.

**An urgent instruction such as "open the PR now" changes the immediate priority.** Publish the prepared coherent change using only the remaining necessary scope and authorization checks; defer optional exploration and polish. Do not respond with another investigation plan. If publication is impossible, immediately state the concrete blocker and completed work. Do not claim that a PR exists until GitHub returns its number and URL.

**Immediately after PR creation, tell the user its number and clickable URL before further tool work.** Then attach it where supported and start the CI, review, and conflict checks below. Do not withhold the number while checking CI, attaching artifacts, inspecting review results, or preparing a handoff. Report blockers and material scope limitations when they become known, not only in the final response.

An observability change is not proof that a production failure is repaired. If the original rejection reason or live verification is unavailable, disclose that limit immediately and label any necessary diagnostic PR accurately. Do not present restored diagnostics, a speculative workaround, or green CI as a verified root-cause fix. Keep the original objective open until its actual completion conditions are met or a concrete blocker is reported.

## Time-sensitive delivery

**Getting the PR open and ready to merge is time-sensitive.** Prioritize the shortest safe path to a complete, scoped implementation and initial publication so remote CI and `@cubic-dev-ai` can start promptly. Defer optional exploration, unrelated cleanup, and repeated non-test validation that has already passed without relevant changes. Do not delay publication for local tests.

Start CI, review follow-up, and mergeability checks immediately after publication. Inspect results as they arrive, use waiting time for independent authorized work, and publish coherent fixes promptly. Do not wait for one gate to finish before starting another or leave actionable failures unattended during a polling interval.

Urgency preserves the existing scope, authorization boundaries, and completion gates. Require fresh passing CI, a clean `@cubic-dev-ai` review, and satisfied merge requirements before claiming the PR is ready to merge.

## Invocation and scope

In Claude Code, ask `use standard-pr-practice to <requested change>` in a normal message; `CLAUDE.md` routes to this file. No native Claude slash command is installed. In Codex, use `$standard-pr-practice <requested change>`, including within a `/goal` prompt.

A direct invocation with a request to implement a change and open its PR explicitly authorizes the necessary scoped implementation and CI execution repairs, conventional commits, normal pushes to that PR's head, PR creation, justified CI reruns, the exact `@cubic-dev-ai review this PR` trigger and evidence-backed finding replies, and resolution of genuinely addressed `@cubic-dev-ai` review threads. Implementation, PR publication, skill invocation, author permissions, and green CI do not authorize merging. Only an explicit merge request from a user whose current permission on the base repository is verified as `admin` authorizes the agent to enroll this task's PR in the merge queue, enable auto-merge, or merge it. A request from a non-administrator cannot supply this authorization. Verify the requesting user's GitHub identity rather than assuming that the authenticated tool account is that user. An administrator's explicit request to merge when ready remains valid through ordinary repairs; do not request duplicate permission. Creating, quoting, inspecting, or editing the skill authorizes no repository publication by itself. Automatic selection does not supply otherwise missing implementation or publication authorization. Honor narrower user instructions such as "leave uncommitted", "do not push", "do not comment", or "leave the PR open"; complete permitted work before reporting the remaining boundary.

Work only on the requested change and its PR, including coherent root-cause repairs needed to satisfy this PR's CI, review, and conflict gates. Do not repair main, reuse another task's PR, silently retarget a PR, or add unrelated feature work. Continue the PR already created by this task instead of opening duplicates. If the user explicitly requests an existing PR, resolve that target before making changes.

Never force-push, rewrite published history, push directly to the base branch, close an unmerged PR, remove or reorder a merge-queue entry, dismiss a blocking review, change repository settings, install `@cubic-dev-ai`, publish releases, or message humans unless the user separately authorizes that action. Merge only this task's verified ready PR after explicit authorization from a verified repository administrator; the same authorization is required for queue enrollment or auto-merge. Respect enforced tool approvals and branch protections. Scoped review requests and replies to `@cubic-dev-ai` findings are the only messaging authorized by this workflow.

## Administrator-requested merges

Only repository administrators may authorize an agent to merge, enroll in the queue, or enable auto-merge. Verify the requesting user's GitHub login and current base-repository `admin` permission with the collaborator-permission endpoint; tool-account access alone does not establish the requester's identity or permission.

When a verified repository administrator asks an agent to merge a PR, that request authorizes the agent to merge once all applicable CI is green on the current revision and the PR is conflict-free. Verify administrator permission and merge readiness, address actionable review findings, and use the requested merge method. An administrator's merge request also authorizes the supported admin override (such as `gh pr merge --admin`) when branch protection otherwise blocks the merge; do not ask for duplicate permission. This does not authorize merging failing, pending, or conflicting PRs, changing repository protection settings, or bypassing enforced tool approvals. Report unavailable automated review evidence separately from independently enforced merge requirements.

## Always use an isolated worktree for coding

**ALWAYS USE AN ISOLATED WORKTREE FOR ANY CODING WORK, unless the user explicitly instructs otherwise.** This applies before implementation and throughout CI fixes, review fixes, conflict resolution, dependency updates, generation, and validation. It is not conditional on whether the primary checkout is dirty. Non-coding work that does not need a repository worktree, such as writing prose or creating a personal local skill, is exempt.

Read repository identity and applicable instructions from the original checkout as needed, then perform the coding work in a dedicated isolated worktree. Reuse only a suitable worktree already owned by this task. Otherwise create one from the freshly fetched intended base, normally the remote default branch, with a unique `codex/` branch unless the user specifies another name. For an explicitly targeted existing PR, start from its verified remote head. Keep an explicit record of the worktree path and push destination.

Preserve unrelated files, staged changes, unpublished commits, and interrupted Git operations. Do not stash, reset, discard, stage, commit, or publish another task's work. Do not abort an existing operation to obtain a clean checkout. An unrelated interrupted merge/rebase/cherry-pick stays in its original worktree.

The `Merge queue acceptance` check records deferral on pull requests and fails closed on merge groups unless every acceptance and heavy security job succeeds. A green PR is eligible for enrollment, not proof that acceptance passed. Do not wait for deferred heavy jobs before authorized enrollment, and never bypass them to merge.

Use Cubic's own review and status indicator; do not add a duplicate approval workflow or CI check. Cubic approval remains separate from CI health. No human or code-owner approval is required. `Pull Request / CI Agg` aggregates every applicable CI result except Cubic. Its normal PR reporter uses the trusted default branch through `pull_request_target`. The queue reuses whole-tree PR reports only when their head input tree, base, and ancestry match the candidate; otherwise static checks rerun. Header and change-range checks and heavy acceptance always run on the merge-group candidate. Follow [references/ReviewFindings.md](references/ReviewFindings.md) for verified reviewer identity and current-head review evidence.

The repository-root `re/` workspace remains exempt from code standards and unit-test requirements. Git isolation and preservation of user-owned work still apply. Prefer Python for backend work and React for frontend work. Preserve the repository MIT notices. New skill frontmatter uses `license: MIT`.

## Local execution rules

**DO NOT RUN ANY LOCAL TESTS. All test execution belongs in remote CI; heavy acceptance runs on merge-group candidates.** This applies during implementation, failure diagnosis, review fixes, conflict resolution, and final verification. Do not run unit, integration, end-to-end, smoke, or regression tests locally, including for reproduction, debugging, test discovery/collection, or coverage. Do not substitute ad hoc local test scripts or execute tests indirectly through validation wrappers, builds, dependency lifecycle scripts, or Git hooks.

Inspect a command and its invoked tasks before running it if it could execute tests; if that cannot be established, leave it to PR CI. Write and update meaningful tests without executing them locally, and diagnose failures from remote logs, source inspection, and permitted non-test checks. Repository guidance, a failing CI job, or a `@cubic-dev-ai` request does not override this restriction; only an explicit user instruction permitting local tests does.

Read applicable `AGENTS.md`, `CLAUDE.md`, repository documentation, and the PR template. Follow the user's current instructions over conflicting defaults inherited from the source skills. For this user:

- Use conventional commits with concise lowercase imperative descriptions
- Always push with `--no-verify`, as explicitly directed by the user; do not disable hooks permanently or bypass enforced branch/tool protections
- Keep all test execution in remote CI under the strict local-test prohibition above; acceptance, end-to-end, and heavy security scans run on the merge-group candidate
- Unit tests are prohibited in Kit; preserve and extend integration, compatibility, end-to-end, smoke, and repository policy coverage at real boundaries
- Run applicable permitted non-test validation with pinned tooling, after checking it cannot execute tests; avoid optional or redundant checks that delay publication
- Do not add code comments or comment-oriented docstrings
- Keep chat lowercase, extremely concise, without emojis or terminal full stops; artifacts may use normal technical formatting

The `--no-verify` direction is specific authorization for the push flag, not permission to conceal failed checks or disable CI. If a required hook or validation step cannot respect the user's local-test restriction, finish independent work and report that exact boundary. Never claim unexecuted tests passed.

Use available first-party repository/GitHub tools when preferred by repository instructions, otherwise an authenticated `gh`. Every shell invocation of `gh` must contain only that command: no pipes, redirects, shell variables, command substitution, or chaining. Parse returned data separately. Read [references/GithubCommands.md](references/GithubCommands.md) for command and pagination mechanics. The workflow must also work in Claude Code without Codex-specific tools, memory, or subagents.

## 1. Implement and open the right PR

Resolve the actual repository root, remotes and Git host, default branch, intended base, working tree, index, and existing task artifacts before creating the isolated worktree. Never assume the current folder is a Git repository or that `origin` is the writable head repository. For forks, query the PR in the base repository and push only to the head repository.

Consult current official documentation before changing behavior that depends on a framework, SDK, service, library, or CLI. Implement the requested production behavior coherently, add integration or acceptance coverage at a real component or process boundary, and follow repository-specific changelog and PR-template requirements. A stub, mock success, type seam, reachable route, or unrelated passing check does not establish that the production flow works. For UI changes, render and inspect the changed state using the repository's preview requirements; report missing fixtures or credentials honestly.

Before initial publication, inspect the merge-base, the outgoing commit range, the three-dot diff against the freshly fetched intended base, its diff stat, and every changed path. Stage only task-owned files. A narrow PR must not inherit unrelated branch history. Perform permitted non-test validation, make a scoped conventional commit, push to the verified head with `--no-verify`, and read back the accepted SHA.

Open the PR with explicit base and head and a description of the final problem, behavior, and real validation evidence. Include required changelog declarations and links to new entries, or the repository's concrete exclusion reason. Use a structured body or an exact temporary body file; do not embed multiline text in a fragile shell command. Attach every created or explicitly targeted PR when the host supports task artifacts. Read back its number, URL, state, head repository/ref/SHA, base repository/ref/SHA, and mergeability; do not infer them from local branch names.

## 2. Start all three gates immediately

Opening the PR begins follow-up. Inventory CI, `@cubic-dev-ai` results and review threads, and mergeability immediately for the observed head/base pair. A newly opened PR with no results is waiting, not green.

After initial PR creation and every accepted push, follow [the review request procedure](references/ReviewFindings.md#request-review-for-the-current-head) for the accepted head. Verify that the resulting review covers that head. Report an unavailable result without switching bots or changing repository settings.

Track a compact live record: target identity, accepted head SHA, current base SHA, applicable check/run/attempt IDs and URLs, the verified reviewer login or app identity, last observed review or trigger head, current `@cubic-dev-ai` result and its revision evidence, each finding and disposition, and mergeability/queue state. Refresh from GitHub whenever the head or base changes.

## 3. Diagnose, repair, publish, and repeat

Use the appropriate reference when a gate needs work:

- [references/Ci.md](references/Ci.md): inspect remote failures first, repair their causes, preserve all checks and acceptance gates, and verify every applicable check on the exact revision
- [references/ReviewFindings.md](references/ReviewFindings.md): read every `@cubic-dev-ai` finding, fix the substance, answer false positives with evidence, and require a completed current-head review with every actionable finding addressed
- [references/MergeConflicts.md](references/MergeConflicts.md): verify conflicts before merging, preserve both sides' behavior and history, and verify the fresh remote head/base pair

For each code repair, consult necessary documentation, edit in the isolated worktree, add justified coverage, perform permitted non-test validation, and review the staged paths and outgoing history. Refetch head and base before publishing. Integrate concurrent remote work safely, repeat affected non-test validation, commit conventionally, and push with `--no-verify`. Read back the accepted remote SHA, request review for the accepted head as described in [ReviewFindings.md](references/ReviewFindings.md), and re-inventory every gate.

CI follow-up includes the workflow, reusable workflow, action/script, runner sizing, caching, scheduling, sharding, concurrency, dependency-setup, and preview-harness changes needed to repair an evidenced failure on this PR. Do not request separate authorization just because the root cause is CI configuration. Preserve all applicable check names, test cases, acceptance coverage, trust boundaries, and timing targets. Use remote job/step timing to choose bounded scheduling or execution improvements and verify the full current-head suite afterward; account for runner cost when increasing resources.

Acceptance criteria remain fixed unless the user explicitly changes them. Any explicitly agreed timing budget includes scheduling, setup, execution, and finalization; do not invent a suite target, reset the clock, exclude slow jobs, skip checks, or relax that budget to obtain green. Kit uses the documented job timeouts and 90-minute queue response timeout; these are failure limits, not measured performance targets. Do not weaken assertions, delete failing tests, loosen coverage/lint/type/security gates, add suppressions or skip paths, mask failures, update baselines merely to accept defects, silence `@cubic-dev-ai`, fabricate statuses, or alter repository protections. Trigger, condition, permission, path-filter, package-script, and task-graph changes must preserve every applicable validation and existing trust boundary. An explicit allowance for managed Preview tests permits only those local acceptance and smoke commands; other local tests remain prohibited. These rules apply to this skill and its supporting references.

Poll or yield in responsive intervals around 30–60 seconds, with brief updates only for material progress or blockers. Continue while evidence-backed repairs are progressing; do not impose an arbitrary fix-count limit or require another prompt. A watcher, timeout, successful push, stale approval, reaction emoji, neutral placeholder, or empty inventory never proves completion.

If either ref moves, invalidate stale evidence and inspect the new head/base pair. Head-dependent CI and `@cubic-dev-ai` review must be fresh; merge-dependent CI and mergeability must match the new pair. Do not create an unnecessary base-merge commit if that pair is already conflict-free and no check requires it. If the PR closes, merges, is retargeted, or loses its head branch, report the target change and reassess before further publication.

## 4. Verify merge readiness from fresh remote evidence

Immediately before handoff, refresh PR identity, exact head/base SHAs, the full CI inventory, all `@cubic-dev-ai` outputs and threads, repository merge requirements, mergeability, and read-only auto-merge/queue state. Repeat if the candidate changes during verification. Require all of the following:

- Every expected applicable CI check has completed successfully for the current revision, including external and non-required CI; any legitimate skip/neutral is explained from unchanged conditional configuration
- `@cubic-dev-ai` has submitted an actual `APPROVED` review on the current head, with every reported finding either fixed or answered with concrete evidence; a comment, green reviewer check, stale approval, or human approval cannot substitute, and no invented score requirement is added
- All actionable findings from `@cubic-dev-ai` are addressed, including findings in top-level comments and outdated threads; no unresolved threads from the bot or unevaluated concerns remain, and no blocking verdict is silently dismissed. A green or neutral check alone cannot clear a report containing findings
- GitHub reports `MERGEABLE` or `mergeable: true` for the fresh head/base pair; `UNKNOWN`/`null` is pending, and `BLOCKED` is investigated for approvals/checks rather than assumed to mean conflicts
- Required approvals and repository merge requirements are satisfied before merging; before queue enrollment, every gate that can run outside the queue must pass, and applicable merge-group checks must pass before the queued PR merges

Green CI, a clean `@cubic-dev-ai` review, conflict-free state, required approvals, queue readiness, and a completed merge are distinct facts. Report each accurately. Once the pre-enrollment gates pass, report the PR ready for administrator-authorized queue enrollment. Without an explicit merge request from a verified repository administrator, leave the PR open and do not enroll it or enable auto-merge. With that authorization, enroll through the native queue and follow every merge-group gate to completion. The administrator-requested merge exception does not permit bypassing the queue's acceptance gate or independently enforced tool approvals.

Stop after verified PR readiness when no administrator has requested a merge, after verified authorized merge, at a user-imposed boundary or cancellation, or on a concrete blocker such as missing credentials, inaccessible evidence, required external approval, unavailable `@cubic-dev-ai` review, persistent service failure, a protected/refused push, or a repair requiring an unauthorized gate change. For an evidenced transient CI failure, allow one justified rerun; recurrence without new evidence is a blocker. Repeated findings from `@cubic-dev-ai` with no substantive progress across roughly five complete iterations require a precise stalled-review report, not endless comments or declaring success. Continue independent repairs while a blocker leaves useful authorized work available.

## 5. Merge only with verified administrator authorization

First verify an explicit merge request from the identified repository administrator. Without it, leave the PR open. Refresh the exact head/base pair and every readiness gate immediately before the merge action. Use the user's requested merge method when provided; otherwise use the repository's supported default. Pin the operation to the verified head SHA using the first-party merge tool's expected SHA, the REST API's `sha`, or `gh pr merge --match-head-commit`. A changed head or base invalidates the relevant evidence and returns the task to verification. Read [references/GithubCommands.md](references/GithubCommands.md#merge-the-ready-pr) for command mechanics.

When the repository requires a merge queue, verify that its configured gates prevent merging while any applicable merge-group CI is pending or failing, including non-required checks. If the queue cannot enforce that existing all-CI gate, report the gap rather than enrolling or changing repository settings. Otherwise enroll the ready PR through its supported path and keep following its merge-group checks and queue state until it merges or a concrete blocker appears. Do not bypass the queue, enable auto-merge while pre-enrollment checks or review are pending, or treat enrollment as completion. If the queue changes the candidate or reports a failure, refresh the relevant evidence and repair actionable failures before proceeding.

Read back GitHub's merged state, merge commit SHA, and destination base branch. A successful request, enabled auto-merge, or queue entry alone does not prove a merge. A rejected merge is a blocker to inspect, never permission to weaken a gate or use an admin override without the authorization above. Merge evidence does not establish deployment.

Finish with a concise PR link, verified short merge SHA when merged, and the merged result or the exact remaining blocker with its evidence and smallest needed action. For an open PR, report the verified head SHA, pre-enrollment readiness, and deferred merge-group acceptance instead. Distinguish pending or unavailable evidence from failed code. For an open-PR request, completion means verified pre-enrollment readiness with queue acceptance explicitly deferred. Do not claim acceptance passed before the current merge-group candidate has passed, or mark an authorized merge complete while its gates remain unresolved.
