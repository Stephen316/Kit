# The four externally defined classes referenced by `Contents/Config-0-ResolvedFeatures`

Closes the gap `Segmentation.md` §3 opened. That work established that the `su_CArchive` map
counter for `ResolvedFeatures` does not start at 1 but at a `base` of 109–112, and that every
class-reference token whose index is **below** `base` names a class defined by a stream read
earlier in the same document load. Those class names were never captured, and the runtime
segmentations record them only as `external#<index>`. A static segmenter cannot compute an
object's byte span without knowing its class, so these four unnamed classes were the single
blocker to static segmentation.

All four are now named. This work is entirely static: no SOLIDWORKS launch, no debugger. It reads
the already-decompiled `Serialize` bodies, the nine recorded segmentations, and the raw stream
bytes of the nine traced parts.

| owning component | **`moUnitComponent_c`** | 43 (8 traces), 45 (`vendor_cojinete`) | 62                        | confirmed  |
| object list      | **`suObList`**          | 82 / 83 / 84 / 85                     | 66                        | confirmed  |

`confirmed` is used in the sense the rest of `re/` uses it: the class is read out of the
decompiled code **and** the byte arithmetic reproduces a real traced object span exactly. Section
4 states, per class, which half of that came from where, including the two cases where the
decompiled call site names a base class rather than the concrete one.

`re/tooling/ghidra/ExtclassResolve.py`, which re-derives every number here from the

## 2. The index is **not** a fixed number and **not** a function of `base`

This matters more than the names, because the static segmenter has to compute the index for an
arbitrary part.

The pre-`base` portion of the map is the class-and-object map of **`Contents/Config-0`**, and
`ResolvedFeatures` continues it. Replaying the traced `Contents/Config-0` node sequence
(`re/data/segments/Differences/NodediffContentsConfigZero.json`, the `boss1..boss3_front_rect_blind` family)
from counter 4 with the `+2 / +1 / 0 / 0` increment rule of `Segmentation.md` §3 gives:

| part                 | `Config-0` nodes | final counter after `Config-0` | traced `ResolvedFeatures` base | `moNodeName_c` | `moUnitComponent_c` | `suObList` | `moPMarkRecord_c` |
| -------------------- | ---------------- | ------------------------------ | ------------------------------ | -------------- | ------------------- | ---------- | ----------------- |
| `boss1` (1 feature)  | 123              | **109**                        | **109**                        | 4              | 43                  | 82         | 102               |
| `boss2` (2 features) | 126              | **110**                        | **110**                        | 4              | 43                  | 83         | 103               |
| `boss3` (3 features) | 129              | **111**                        | **111**                        | 4              | 43                  | 84         | 104               |

The final counter of `Config-0` equals the `ResolvedFeatures` base exactly, for all three
feature counts, with no fitted constant. That is the proof that the two streams share one index
space, and it also reproduces the four external indices of the 1-, 2- and 3-feature traces
(`baseline` / `circle` / `planetop` → 4, 43, 82, 102; `twopad` / `cutbase` / `padplane` →
4, 43, 83, 103; `three` → 4, 43, 84, 104).

The mechanism behind the drift is the per-feature growth `Multistream.md` §3 measured in
`Config-0`: three nodes are inserted per feature (`null`, `null`, `classref moAtom_c`), worth
`0 + 0 + 1` counter units. So every class `Config-0` defines _after_ that insertion point shifts
by **+1 per feature** and every class defined _before_ it does not:

- `moNodeName_c` is the **first** class definition of `Config-0`, at counter 4 — constant in
  every part observed, which is why index 4 never moves.
- `moUnitComponent_c` (definition 20) and everything up to `moAtom_c` sit before the insertion
  point — constant at 43 across eight traces.
- `suObList` (definition 32) and `moPMarkRecord_c` (definition 37) sit after it — 82→83→84 and
  102→103→104.

`vendor_cojinete` breaks the arithmetic that would tempt you to write `base - 27`: its indices
are 4, **45**, **85**, **106** at `base` 111. Its `Config-0` has 39 class definitions rather than
40 (no `moCThreadRefMgr_c`) and a different object population, so all three movable indices land
elsewhere and the shifts (+0, +2, +3, +4) are not uniform. `vendor_ring` is a third pattern
again: 4, 43, **83**, **104** at `base` 111.

**Rule for the static segmenter:** resolve these indices by _name_, by segmenting
`Contents/Config-0` first and continuing its map into `ResolvedFeatures`. Do not hardcode 4, 43,
82, 102 and do not compute them from `base`. The class-definition _order_ inside `Config-0` was
compared in full for `BASELINE_40x20x10` and both V8 vendor parts and is identical in all three,
so in those parts the four classes are the 1st, 20th, 32nd and 37th definitions of that stream
(`COJINETE INFERIOR` omits `moCThreadRefMgr_c`, which sits after all four). The ordinals look
stable; the indices demonstrably are not. Three parts is not the corpus, so treat the ordinals as
observed rather than guaranteed.

Index 4 is the one safe constant, and it is safe because it is structural: the first class
definition of `Config-0` is `moNodeName_c` in every part scanned.

## 3. Method

Three independent chains, run against the same nine recorded segmentations.

**Chain A — the parent's decompiled `Serialize` names the child.** Every external class
reference row carries `parent` and `depth`. The parent is an in-stream object and _is_ named, so
`SerializeMap.json` gives its `Serialize` address and the decompiled body says which class it
constructs at that position. The child order in the code has to line up with the child order in
the segmentation, and it does in all four cases.

**Chain B — the `Contents/Config-0` map replay.** Section 2. Independent of the decompiler:
it uses only the traced node sequence, the published increment rule, and the traced
`ResolvedFeatures` bases.

**Chain C — the corpus-wide class-definition scan.** A class reference can only name a class some
stream of the same document defined. Scanning every stream of 108 parts for `ff ff 01 00 <len>
<name>` definitions gives a hard presence test:

| class               | defined by name in |
| ------------------- | ------------------ |
| `moNodeName_c`      | 108 / 108 parts    |
| `moUnitComponent_c` | 108 / 108 parts    |
| `suObList`          | 108 / 108 parts    |
| `moPMarkRecord_c`   | 108 / 108 parts    |
| `moComponent_c`     | **0 / 108 parts**  |
| `moAsmFeatData_c`   | **0 / 108 parts**  |

The four answers are universally present; the two base-class / wrong-hypothesis candidates that
the decompiled code mentions at those call sites are universally absent. This chain cannot pick a
class on its own, but it eliminates candidates decisively, and it is what settles §4.2.

**Corroboration — the stream bytes.** All nine traces were matched to their original parts by
path from the segmentation JSON and re-extracted with `streamlib.load_donor`. Every one is
byte-exact against the traced `stream_length`:

| trace             | part                              | stream bytes |
| ----------------- | --------------------------------- | ------------ |
| `baseline`        | `BASELINE_40x20x10.SLDPRT`        | 11075        |
| `circle`          | `CIRCLE_r10.SLDPRT`               | 10556        |
| `planetop`        | `PLANE_TOP.SLDPRT`                | 11075        |
| `twopad`          | `TWOPAD_d5.SLDPRT`                | 19390        |
| `cutbase`         | `CUTBASE_cd5.SLDPRT`              | 16579        |
| `padplane`        | `PADPLANE_rev_d5.SLDPRT`          | 16581        |
| `three`           | `THREEFEATURE_pad_cut_pad.SLDPRT` | 24805        |
| `vendor_ring`     | `Piston Ring KF.SLDPRT`           | 25998        |
| `vendor_cojinete` | `COJINETE INFERIOR.SLDPRT`        | 17601        |

So no fixture substitution was needed and no approximate match was used. `examples/Fixtures/SolidWorks/donors/boss1_front_rect_blind/resolved.bin` is 11073 bytes against `baseline`'s
11075 and is **not** the same part; it was not used. The `boss1..boss3` fixtures do back the
`Config-0` node sequences of §2, which came from the `Multistream.md` trace of that family.

### One caveat about lengths that has to be stated

A segmentation row's `length` is the distance to the _next_ `ReadObject` event, not the object's
own body length. When an object is the last read of its parent's frame, every raw byte the
ancestors read afterwards is absorbed into that row. So the traced spans are exact object
boundaries — the tiling and re-emit proofs in `Segmentation.md` depend on that — but they are an
**upper bound** on an individual object's body.

This is what made `suObList` look like three different classes at first: the same class index
appears with spans of 4, 63 and 174 bytes. The 4-byte spans are lists followed immediately by
their elements; the 63- and 174-byte spans are empty lists that happen to be the last read of
their frame. Both shapes agree once the absorption is accounted for, and the tables below quote
_own body_ lengths derived from the decompiled `Serialize`, separately from the traced spans.

## 4. Evidence per class

### 4.1 `moNodeName_c` — index 4, 216 instances

Read by `moNode_c::Serialize` @ `0x4c1db8f0` as its first child:

```
pCVar10 = su_CArchive::ReadObject(param_1,(CRuntimeClass *)&moNodeName_c::classmoNodeName_c);
*(CObject **)(this + 0x18) = pCVar10;
```

The class name is literal, as the `CRuntimeClass` argument. `moNodeName_c::Serialize` @
`0x4c1db8a0` is two lines long and reads **exactly one `CString`**, so its own body is
`4 + 2·cch` bytes.

Byte check, all 216 instances across all nine traces: the two bytes after the tag are the
`ff fe ff` wide-string marker, the following byte is the character count, and the
`2·cch` bytes after that decode as UTF-16LE. Own bodies run 8–52 bytes. Traced spans run 30–78
bytes; the difference is a constant 20 or 24 bytes of node scalars that `moNode_c::Serialize`
reads _after_ the child returns (`u32`, `u32` flags, `u32` id, `u32`, empty `CString`, `u32`),
which is the absorption effect of §3.

Worked example, `BASELINE_40x20x10` segment 1 at offset 30, span 46:

```
2c 80                                            classref, index 4
ff fe ff 08 43 00 6f 00 6d 00 6d 00 65 00 6e 00  CString "Comments"        moNodeName_c body, 20 bytes
74 00 73 00
00 00 00 00 00 00 00 40 08 00 00 00 00 00 00 00  moNode_c scalars: flags 0x40000000, id 8
ff fe ff 00 00 00 00 00
```

`2 + 20 + 24 = 46`. The `0x40000000` / `0xC0000000` flag words and the tree ids here are the same
fields `streamlib`'s `BOSS_FLAGS` / `PLANE_FLAGS` constants and `resolved.tree_nodes` already
key on, which is why this record was legible long before the class had a name.

Parents: every tree node — 19 distinct classes, from `moCommentsFolder_c` and `moRefPlane_c`
through `moExtrusion_c`, `moICE_c` and `moLengthParameter_c`. That is exactly the reach of
`moNode_c`, the common base.

### 4.2 `moUnitComponent_c` — index 43 (45 in `vendor_cojinete`), 62 instances

Read by `moCompRef_c::Serialize` @ `0x4bc22f00`, immediately after the base `su_CObject::Serialize`:

```
::operator>>(param_1,&local_48);
*(CObject **)(this + 0x58) = local_48;
```

a polymorphic read into the member at `+0x58`, which the rest of the function treats as a
`moComponent_c *` (`moComponent_c::getFiledOwner(pmVar12)`, `IsKindOf(moUnitComponent_c)`).
`moComponent_c::Serialize` @ `0x4c279a90` on the load path reads **one nested object and no
scalars**:

```
LAB_4c279dae:
  local_res20 = (CObject *)0x0;
  ::operator>>(param_1,&local_res20);
```

Byte check, all 62 instances: the traced span is **exactly 2 bytes** — tag only, zero own body —
and the next segment is always a nested object one level deeper, always an _object reference_
(the document object, already in the map from `Config-0`). That is the single nested read of
`moComponent_c::Serialize` and nothing else.

Parents: `moCompFeature_c`, `moCompRefPlane_c`, `moCompSolidBody_c`, `moCompEdge_c`,
`moCompFace_c`, `moCompSketchEntHandle_c` — the `moCompRef_c` subclasses, and only those.

**Concrete class versus base class.** The decompiled call site names `moComponent_c`, the
declared type of the member, not the class actually instantiated. Two further measurements pin
the concrete class:

1. A static `ff ff` class-definition scan of **every stream of 108 parts** — the 51-part authored
   corpus, `corpus2`, and all 57 V8 vendor parts — finds `moComponent_c` defined in **0 of 108**,
   so it cannot be the referent of any class reference in any of those documents.
   `moUnitComponent_c` is defined in **108 of 108**, in `Contents/Config-0` and in
   `ThirdPtyStore/VisualStates`.
2. The `Config-0` replay of §2 puts `moUnitComponent_c` at index 43 in `boss1`, `boss2` and
   `boss3` — the observed index.

`moUnitComponent_c::Serialize` @ `0x4c288670` calls `moComponent_c::Serialize` first and adds
its own fields afterwards, so the observed 2-byte span with an immediate nested read is
consistent with the subclass, not only with the base.

### 4.3 `suObList` — index 82 / 83 / 84 / 85, 66 instances

Read by `moSketchRegion_c::Serialize` @ `0x4b9d81e0`, which reads exactly one child:

```
operator>>(param_2,(suObList **)(param_1 + 8));
```

and by `sgSketch::Serialize` @ `0x4c5d28c0`:

```
::operator>>(param_1,(suObList **)(this + 0x5d0));
```

after which `sgSketch` walks the list and calls `moSketchRegion_c::iSetSketch` on each element —
so `sgSketch + 0x5d0` is the list of sketch regions and `moSketchRegion_c + 8` is the region's
boundary-entity list (the store path names it, `ScopedObjContext(..., "BoundaryEnts", ...)`).

Byte check. The body opens with a `u16` element count. Of the 66 instances, 36 are followed by
nested objects and in every one of those the count equals the number of immediate children
exactly; the other 30 have count `0` and no children. `moSketchRegion_c` has exactly one child
in every trace, and it is this class.

Worked example, `BASELINE_40x20x10` segments 200–206:

```
7633  52 80 01 00                  suObList, count 1
7637    ff ff 01 00 ... moSketchRegion_c   the one element
7659      52 80 04 00               suObList, count 4
7663        sgLineHandle  sgLineHandle  sgLineHandle  sgLineHandle
```

Parents: `sgSketch`, `moSketchRegion_c`, `sgCircleDim`, `sgLLDist`, and rows the trace attributes
to a `null` tag (a null tag has no `Serialize`, so those rows' parent attribution is an artefact
of the `@rsp` bucketing; the reads belong to an ancestor frame).

The name is not literal at the call site — the read is polymorphic and `suObList` is Ghidra's
type for the member. It is pinned the same way as §4.2: `suObList` is defined by name in
`Contents/Config-0`, `Contents/CMgr`, `Contents/Config-0-ModelHeader` and `Header2`, and the
`Config-0` replay puts it at 82 / 83 / 84 for `boss1` / `boss2` / `boss3`, matching the observed
indices of the 1-, 2- and 3-feature traces. `Multistream.md` §3 already segmented a named
`suObList` definition inside `CMgr` and `ModelHeader`, so the class is not new to this corpus —
only its identity inside `ResolvedFeatures` was missing.

### 4.4 `moPMarkRecord_c` — index 102 / 103 / 104 / 106, 13 instances

Read by `FUN_4bb886c0`, the base `Serialize` that `moBodyFeature_c::Serialize` @ `0x4bb8aa10`
invokes as its first statement:

```
su_CArchive::AR_get_int(param_2,(int *)&local_res18);
if ((uint)local_res18 != 0) {
  operator>>(param_2,(moPMarkRecord_c **)(param_1 + 0x3c8));
  su_CArchive::AR_get_int(param_2,(int *)&local_res20);
  su_CArchive::AR_get_int(param_2,(int *)(param_1 + 0x3c0));
  su_CArchive::AR_get_int(param_2,(int *)(param_1 + 0x578));
}
```

The name is literal both here and in the demangled extraction operator
`??5@YAAEAVsu_CArchive@@AEAV0@AEAPEAVmoPMarkRecord_c@@@Z`, which calls
`ReadObject(param_1,(CRuntimeClass *)&moPMarkRecord_c::classmoPMarkRecord_c)`.
`moPMarkRecord_c::Serialize` @ `0x4bb97ca0` reads **exactly one `long`** on the load path, so its
own body is 4 bytes — the `gcPMark_w` id.

Byte check, all 13 instances across all nine traces: the four bytes immediately **before** the
tag are `01 00 00 00`, the guard int that gates the read, and the four bytes after the tag are
the id. Ids are 5 and 8 in the corpus parts, 26 and 29 in `Piston Ring KF`, 8 in
`COJINETE INFERIOR`.

Worked example, `BASELINE_40x20x10` around offset 8963:

```
8959  01 00 00 00     guard int, non-zero
8963  66 80           classref, index 0x66 = 102
8965  05 00 00 00     moPMarkRecord_c body: pmark id 5
8969  ...             three AR_get_int, then the rest of the base Serialize
9021  00 00           null tag: ReadObject(moAsmFeatData_c) returns nothing
9031  ff ff 01 00 0b 00 "moEndSpec_c"
```

Parents: `moExtrusion_c` and `moICE_c` only — one instance per body feature, which is why the
count is 1 for the single-solid-feature parts and 2 for the boss+cut parts. The traced span is 58
bytes in every instance; 4 of those are the object, the remaining 52 are the guard's three ints
and the tail of the base `Serialize`, absorbed per §3.

The `00 00` at 9021 also explains a dead end worth recording: `moBodyFeature_c::Serialize` calls
`ReadObject(&moAsmFeatData_c::classmoAsmFeatData_c)` right after, and `moAsmFeatData_c` was the
first hypothesis for this slot. It is wrong. `moAsmFeatData_c` is defined in no stream of any part
scanned, and the read is a null tag in every traced part — assembly feature data is absent from a
part document.

## 5. What is still unknown

1. **The `Config-0` node sequence is traced for one family only.** §2 replays
   `boss1..boss3_front_rect_blind`. That is enough to prove the continuation (the final counter
   matches the base for three different feature counts) and enough to reproduce the indices of
   the seven corpus traces, but the two V8 vendor parts' indices (45 / 85 / 106 and 83 / 104) are
   _explained_ by the model rather than _recomputed_ from it, because no `Config-0` segmentation
   exists for those parts. Their slot assignment rests on Chain A and the byte signatures, which
   are unambiguous per class — `ExtclassResolve.py` refuses to emit if any index matches more
   than one signature — but the numeric index is not independently re-derived. One
   `Multitrace.py` run per vendor part on `Contents/Config-0` would close that.
2. **`Config-0` cannot yet be segmented statically.** The rule in §2 is only useful to a static
   segmenter once `Contents/Config-0` can be segmented without a debugger, and that stream has
   its own set of classes whose layouts are not all recorded. The dependency is now explicit and
   one-directional: static `ResolvedFeatures` needs static `Config-0`, which needs the layouts of
   the 40 classes `Config-0` defines.
3. **`suObList` element typing.** The count-then-elements shape is confirmed here, but
   `Multistream.md` §3 records an `suObList` in `CMgr` whose body is `u16 0, u32 count` followed
   by _inline_ 12-byte entries rather than nested objects. Both are the same class name. Which
   shape a given `suObList` takes is presumably decided by the owner, and that is not
   characterised. `suObList::Serialize` itself lives in `sldmfcu.dll` and was not decompiled for
   this work.
4. **Whether four is the whole set.** Four distinct external class indices is what the nine
   recorded segmentations contain. A part using features outside this corpus — patterns, fillets,
   sheet metal, configurations beyond `Config-0` — may reference further `Config-0` classes that
   never appear here. The four are the complete set _for these nine parts_.
5. **Object references below `base` are not covered.** `Segmentation.md` §3 counts 6, 12 and 14
   external _object_ references alongside the class references. Those are individual objects from
   `Config-0`, not classes; naming them is a different question and is untouched here.

2-byte span with one nested object, `u16` count equal to the child count, `01 00 00 00` guard)
each match exactly one of the four indices in each of the nine traces, and the script raises if
that stops being true.

existing `re/solidworks/` document was modified. `re/tooling/harness/Streamlib.py` and
