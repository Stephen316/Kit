### Saved study findings

Study scripts, reports and capture paths in this section are relative to [the Study directory](../Study/README.md).

`face-edit-decoding.json` covers seven examples in `faceedits-3f120cbee8d9`: positive/negative/multiple-face/cylindrical offsets, two plane replacements with opposite tangent-chain flags, and deletion of a hole wall. Offset values follow explicit numeric bindings. Counted selection proxies and their descriptors have reciprocal feature owners; their item counts match the direct input faces in these examples. Replacement construction planes resolve through typed native references and match the API plane geometry. The opaque solid-face descriptors are retained without claiming a persistent face-to-ASM mapping. At this initial stage, delete-face healing controls and replacement surface/body targets remained unverified; the later ReplaceFace sheet-target contrasts qualify the captured face/body variants separately.

`surface-tool-decoding.json` adds eleven examples in `surfacetools-856ca50cf4c7`. Rectangle/circle patches reuse explicit sketch-profile loop membership. Surface offsets expose signed distance bindings, chain selection and sharp/rounded flags. Two open-sheet stitches validate tolerance bindings and matching operation-flag copies on their owned selection proxies; the stored operation is retained without treating it as active because the API ignores it for open-sheet results. Unstitch validates its chain flag and records expanded selections: one API input face expands to six native face descriptors in the chain example. These descriptors and result-record references are not interpreted as the original input count or final body identities. Normal reversal and surface deletion expose owned selection lists with distinct typed feature identities. Patch continuity/rail controls, offset operation encoding and general regeneration remain unsupported.

`boundary-fill-decoding.json` compares nine cases in `boundaryfills-a0953038318b`: selected overlap/outer cells, multiple cells, join/cut/intersect/new body, tool removal, a plane tool and component mode. All nine operations, removal flags and tool/selection counts match the API. Eight closed-box cases also match the two native body-membership groups against API cell bounds; these observations do not establish general inside/outside semantics. Cell keys are not API cell-array indices. The API normalizes the requested new-component operation to new-body plus component wrappers. Native face recipes, plane recipes and component-context bytes are retained without claiming exact boundaries or regeneration. The first getter-failure attempt is retained in `boundaryfills-8ab7ff242e08`.

`boundary-plane-decoding.json` resolves the plane-tool variant through an owned proxy, a 252-byte descriptor and a typed terminal into independently decoded `ToolPlane` geometry. The recovered origin at 1.2 cm along X and its normal match the generator and selected API-cell boundary. Five focused checks and three rejection guards support this one observed layout. Descriptor metadata, occurrence context and general plane-side semantics remain unresolved; no new fixture generation is required.

`thicken-decoding.json` compares eight exported cases in `thickenmodes-552efbb83fca` and `thickenmodes-17612e4ff890`: positive/negative thickness, symmetry, chaining, Sharp/Rounded, whole-sheet-body input and Join/Cut/Intersect with separate solid participants. Signed stored parameters and flags match the API; typed face recipes/body descriptors link inputs to native historical bodies, and explicit result anchors check back to their source feature. The initial three rejected solid-face inputs remain in the first capture's ground truth. Three malformed cases are rejected and the earlier Thicken fixture remains supported. **Symmetric parameter normalization is unresolved:** the requested 2 mm case stores/exposes 0.4 cm while the exported geometry provides separate bounds/volume evidence. The decoder retains the stored value without deriving symmetric offsets or physical wall thickness. Exact faces, participant-body roles and thickened geometry regeneration remain unsupported.

`boundary-fill-result-decoding.json` recovers ten explicit result-body associations in nine existing captures. Six NewBody cases have counted feature-owned result anchors. Join instead has a distinct result proxy selecting two historical bodies, while Cut and Intersect select one each; a zero owned-anchor count therefore does not imply zero API results. Stored result counts/names and nine available result-vertex bounds comparisons corroborate these roles. The plane-first case identifies native result 355 explicitly while its preexisting incomplete ASM token stream still prevents geometry association. Five malformed guards reject broken counts, owners and repeated collection membership.

Boundary Fill removal actions provide a useful lifecycle distinction: native bodies 275/354 retain a collection pointer but are absent from both repeated collection lists, while result 442 is listed. Other saved BaseFeature and Mirror PM/DM pairs can both remain listed in distinct collections. These are literal stored membership/removal facts, without a universal current-visible/final-body rule. The integrated `boundary_fill_results` summary retains this provenance and adds successful owned/result-selection counts and identities to existing settings.

`support-result-integration.json` records twenty-five focused main-reader comparisons across twenty-five saved archives, including the fourteen Hole and nine Boundary Fill examples, both path planes and the imported-root recovery. No new live capture ran. The corpus remains 559 archives and 369 native class GUIDs; general writing, complete translation, reconstruction and unsupported feature variants remain unfinished.

`sculpt-tool-attribute-decoding.json` decodes the 297 typed sculpt face attributes with reciprocal owner chains and 593 literal journal mentions across nine saved Boundary Fill archives. Geometry pointers use a separate ordinal table of initial and trailing geometry entities, excluding history entities and markers; global inspection indices and delta-state journal slots remain explicit separate fields. The helper validates face/shell/lump/BODY membership, attribute next/previous chains and bounded reciprocal journal neighbor links. All 297 payloads replay exactly; 1,537 focused checks include five malformed guards and an attribute-free component-history control.

The sculpt tags record face source provenance, not the identity of their owning snapshot BODY: every such BODY is unnumbered, and one can contain faces tagged with multiple native tool numbers. Separate typed native selections corroborate 292 positive body-source values and four positive workplane values; the lone -282 literal retains only a magnitude coincidence with the selected plane. Polarity, journal transition sides, chronological direction, current/final classification and replay remain unknown. Optional `asm_decoding.streams[].sculpt_tool_attributes` exposes these scoped records. A semantic provenance error is reported there without changing token completeness or initial topology. `sculpt-tool-integration.json` checks all nine populated summaries plus one attribute-free history stream and a deliberately unknown attribute-name control.

`boundary-sculpt-provenance-decoding.json` publishes 296 positive sculpt-face source correspondences through independently typed Boundary Fill selections. Raw mapping entries, collection ownership and filenames prove the exact same-asset history blob. Counted body-tool proxy/descriptor/anchor chains and plane proxy/descriptor/terminal chains identify the selected native sources. The initial auxiliary workplane face carries source-plane 282 provenance while its own ASM BODY remains unnumbered. The negative literal -282 remains in `unresolved_attributes` with magnitude-only candidates. The decoder preserves owner entity ordinals, global indices and snapshot BODY identity separately, without assigning exclusive feature causality, current/final lifecycle or persistent face identity. Nine archives, two empty controls and five malformed guards pass 2,437 focused checks. Main output exposes `boundary_fill_sculpt_provenance` and explicitly keyed per-feature annotations.

`patch-continuity-decoding.json` adds three circular B-rep edge Patch exports with actual Connected, Tangent and Curvature controls. A typed per-edge definition links its explicit owner to the boundary proxy, edge recipe and historical body anchor. A separate feature-owned result anchor establishes result provenance. The common surface reader retains operation/count validation and opts into this boundary grammar without changing the old sketch-profile branch. The stored scalar agrees with the sole captured weight .5 but remains uncontrasted; group and flip fields remain raw. A newly observed circular context cache stays opaque. Actual Tangent/Curvature result areas and bounds slightly differ from an ideal planar circle; those counterexamples are retained without claiming solved surface geometry. Main `patch_continuity` restores only these bounded settings and their corresponding old layout errors. The first capture's PathEntity serialization failure is retained alongside the corrected successful exports and exact executed source snapshots.

`stitch-hint-attribute-decoding.json` resolves four Patch EDGE diagnostics with an exact terminal `stitch_hint-sys-attrib` sibling. The independent reader verifies the two-node EDGE→generic→hint chain and all reciprocal pointers before the shared naming reader accepts it. Three finite typed doubles remain literal payloads without tolerance, distance, direction or solver meaning. Each complete 99-byte record, 72-byte typed field region, 27-byte numeric region and counted generic naming payload replays at its actual original blob offsets. Twenty previous naming dictionaries, three control blobs and eight malformed helper/production guards pass.

`GenerateReplaceFaceTargetContrasts.py` produced three actual exports in `replacefacetargets-670e35eedbc8`: single Patch face target, whole sheet-body target, and the face target with tangent chaining enabled. All three ReplaceFace features are healthy, their local exports succeed and their owned documents close successfully. The source block changes from 2 cm to 1 cm high, while the independent oversized sheet remains a second body at z = 1 cm. Actual createInput argument types, input and rolled feature getters, independent bodies, geometry, source/SDK snapshots and export hashes are retained. The face argument becomes a collection in the feature target getter, while the body argument stays a BRepBody; native face and body descriptors remain distinct. API representations, native references and result geometry stay separate observations.

`replace-face-target-decoding.json` qualifies three captured sheet-target definitions using a bounded optional target resolver in the existing face-edit reader. The default plane-target branch, source selection codec, header counts and tangent flag remain unchanged. The opt-in admits only one typed face or body target descriptor with reciprocal ownership; source and replacement BODY roles are independently checked. Face arguments become a collection in the rolled feature getter, while whole-body arguments remain BRepBody; native descriptor classes identify each stored representation separately. Eight malformed guards pass, and all seven prior complete default settings remain exact against `7b2daac` and their historical report: four OffsetFaces, two construction-plane ReplaceFace and one DeleteFace controls. Other targets/contexts, persistent selected-face mapping and regeneration remain unresolved.

`replace-face-body-route-decoding.json` independently qualifies three historical source BODY routes, three separate Patch replacement BODY routes and six current stored BODY-to-ASM associations. Seventy focused checks and six malformed guards pass, and all seven old face-edit controls have no false matches. Face targets retain their owned recipe/context chains; body targets retain a separately typed namespace/context/link/identity-leaf route that agrees with the anchored BODY. The canonical native body/blob reader and explicit stored ASM identifiers establish the mappings. Replacement BODY 379 maps to ASM record 3, while auxiliary unnumbered BODY record 2 stays unassigned. Complete current planar geometry agrees collectively with the API, including the unchanged target sheet. No per-body API/native identity, persistent selected ASM face, newly owned ReplaceFace result anchor, source/result pairing or general lifecycle is inferred.
